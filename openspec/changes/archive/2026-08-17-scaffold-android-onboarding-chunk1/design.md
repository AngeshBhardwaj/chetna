## Context

`apps/mobile/android` doesn't exist. `apps/domains/{consent,enforcement,credits,device}` are JVM-only KMP modules today, each carrying a comment anticipating an `android()` target. `apps/backend`'s `build.gradle.kts` shows the established pattern for consuming domain modules (`implementation(project(":domains:consent"))`) and for extra test source sets (the `jvm-test-suite` plugin's `testing { suites { ... } }` DSL, not manual `sourceSets {}`). No Gradle CI exists in this repo at all yet. No lint/static-analysis tooling exists anywhere in `apps/`. ADR-0015 and ADR-0016 (both `docs/content/documentation/adr/`) already settled the architectural questions this design implements against; this document is the concrete "how," not a re-derivation of the "why."

Two references exist for these four screens, and they carry **different, non-interchangeable authority** — this distinction was corrected after an initial misstatement in this change's own `proposal.md`, and must not be re-conflated during implementation:
- `design/prototype/reference/onboarding/welcome-and-auth/screen-exports/*.png` — the **authoritative visual/interaction reference**: native-feeling layout, spacing, alignment, component placement, edge-to-edge status bar treatment, bottom-anchored full-width buttons. These are the target look.
- The React/MUI prototype (`design/prototype/src/screens/onboarding/`) — a **secondary reference, for content wording and interaction logic only** (screen sequencing, OTP auto-advance/retry/lockout state machine, consent-gating, resend countdown), plus the wiring to `design/tokens/`. It is explicitly **not** authoritative for visual fidelity: being a web/MUI app, it could not fully reproduce native look-and-feel, alignment, or interaction fidelity even after being reworked once already against these same reference PNGs earlier this session (see the design-phase-plan's "diff against external references" rule). Where the prototype's layout and the reference PNGs disagree, the PNGs win.

Per ADR-0013, the prototype's job was always design *communication*, not a code or pixel source — this session's earlier prototype-vs-reference diffing pass is the concrete precedent for why the PNGs, not the prototype, are the visual bar for the native build.

## Goals / Non-Goals

**Goals:**
- A real, running `apps/mobile/android` Gradle module producing an installable debug APK.
- The four Chunk 1 screens (Welcome, Contact details, OTP verify, Signed-in) as native Compose UI, visually matching the reference screen-exports (`design/prototype/reference/onboarding/welcome-and-auth/screen-exports/*.png`) — layout, spacing, alignment, native component treatment — while following the prototype's validated content and interaction logic (icon badge as a concept, selection card, boxed auto-verifying OTP with 3-attempt retry/lockout). The PNGs are authoritative for look; the prototype is authoritative for content/behavior only.
- The Compose theme generated from `design/tokens/`, not hand-written.
- A reproducible Dockerized emulator (`Dockerfile`, not just the manually-committed local image from this session's investigation) for development-time verification.
- Full test-level coverage for what's built: unit (ViewModels/business logic) and instrumented (`androidTest`, Compose UI tests for the trickier interaction — OTP retry/lockout).
- Minimal CI (unit tests + `assembleDebug`) so the module doesn't silently rot unbuilt.

**Non-Goals:**
- No real backend auth endpoint — auth stays mocked (matching the prototype's hardcoded-code check). Explicit follow-up after this UI is signed off.
- No Play Store account/listing work (ADR-0016 — user-only action, separate from this change).
- No multi-module Gradle split, no Koin, no Compose Multiplatform navigation — ADR-0015 already rejected these.
- No detekt cleanup of `backend`/`domains` — new module only.
- No iOS work.

## Decisions

- **Package structure**: `in.chetna.mobile` root (matches the existing `group = "in.chetna"` in the root `build.gradle.kts`), then per-feature: `in.chetna.mobile.onboarding.welcome`, `.contact`, `.otp`, `.signedin`, plus `in.chetna.mobile.ui.theme` (generated `Color.kt`/`Shape.kt`, hand-written `Typography.kt` left at M3 defaults), `in.chetna.mobile.navigation` (the `NavHost`/route definitions), `in.chetna.mobile.di` (Hilt modules).
- **Gradle wiring**: `apps/settings.gradle.kts` gains `":mobile:android"`, plus a `pluginManagement`/`dependencyResolutionManagement` block adding `google()` (verified necessary — AGP and AndroidX artifacts aren't on the Gradle Plugin Portal or Maven Central, only Google's Maven repo; the build fails to resolve `com.android.*` plugins without it). The four domain modules' `kotlin {}` blocks gain an Android target alongside the existing `jvm()` — **verified empirically, not from docs, which disagreed with each other**: AGP 9.0+ requires KMP modules to use the `com.android.kotlin.multiplatform.library` plugin with an `android { namespace; compileSdk = 36; minSdk = 26 }` block inside `kotlin {}`, not the legacy `com.android.library` + `androidTarget()` combo this design originally specified (that combo needs `android.enableLegacyVariantApi=true` and is removed entirely in AGP 10). This puts AGP (and an SDK requirement) on the classpath of every consumer, including `apps/backend` — confirmed harmless: `apps/gradlew-docker :backend:build` still succeeds cleanly. `apps/mobile/android/build.gradle.kts` applies `com.android.application` (a plain Android app module, not KMP — its `test`/`androidTest` source sets stay the classic names, unaffected by the domain modules' KMP-specific plugin choice), Kotlin, the Compose compiler plugin, and Hilt's Gradle plugin; depends on all four `:domains:*` modules via `implementation(project(":domains:x"))`, matching `apps/backend`'s existing pattern. `compileSdk`/`minSdk` apply to `apps/mobile/android` too, for consistency with the domain modules.
- **Android SDK + JDK provisioning**: containerized, not host-installed — **corrected during implementation** from this design's original host-installed-SDK decision, after finding this machine has no JDK at all and never has, matching `apps/backend/Dockerfile`'s existing precedent of building Kotlin/JVM code inside a `gradle:8.11-jdk21` container rather than on host. Concretely: `apps/gradlew-docker`, a thin wrapper script committed at the `apps/` root, runs `docker run --rm -v <repo>:/workspace -w /workspace/apps -e ANDROID_HOME=/opt/android-sdk-linux <image> ./gradlew "$@"` against `saschpe/android-emulator:<verified tag>` (verified directly this session: JDK 23 + `sdkmanager` + platform-tools already present at `/opt/android-sdk-linux`, mounting the repo and running `./gradlew --version` against it works). Every `./gradlew` invocation named anywhere in this design or in `tasks.md` means "via `apps/gradlew-docker`," not a bare host `./gradlew` — not restated at each call site. Host installs only `adb` (platform-tools) for the physical-device sideload step (approved as a small, narrow host install — USB access can't be containerized). CI needs no separate provisioning: GitHub-hosted `ubuntu-latest` runners already ship an Android SDK, so `.github/workflows/android.yml` runs directly on `ubuntu-latest`, not inside a bare `gradle:*-jdk21` container (no SDK, would fail `assembleDebug` immediately) and not inside the emulator image either (CI needs no display/VNC layer, and `ubuntu-latest` already has SDK+JDK).
- **`connectedAndroidTest` runs inside the emulator's own container**, not a separate build container. **Corrected twice during verification**: `adb connect <host>:5555` doesn't work (emulator ports are loopback-only); a remote adb server (`adb -a start-server` + `ANDROID_ADB_SERVER_ADDRESS`/`PORT`) works for the plain `adb` CLI but not for AGP's own device discovery (`DeviceMonitor`/ddmlib ignores those env vars — confirmed directly, hangs on "Cannot reach ADB server"). Real Dockerized Android CI projects run build+emulator in one container for this reason; `emulator/compose.yaml` mounts the repo + `chetna-gradle-cache` so `docker exec chetna-android-emulator ./gradlew :mobile:android:connectedDebugAndroidTest` works directly. `apps/gradlew-docker` (used for everything else — build, unit tests, detekt) has no emulator-networking logic at all. Host `adb` is reserved for the physical-device sideload path only, where there's no other option.
- **Theme generation**: extend `design/tokens/generate-scheme.mjs` (or add a sibling script in `design/tokens/`) to also write Kotlin output — reading the same `tokens.json`/`generated/color-scheme.json` already produced for the web prototype, emitting `Color.kt` (`lightColorScheme()`/`darkColorScheme()` calls built from the M3 role hex values) and `Shape.kt` (from `tokens.json`'s `shape.radius`) directly into `apps/mobile/android/src/main/kotlin/in/chetna/mobile/ui/theme/`. Generated files carry a "do not hand-edit" header, matching `generate-scheme.mjs`'s existing convention for `color-scheme.json`. **Committed, not gitignored** — matching the existing precedent that `design/tokens/generated/color-scheme.json` is itself committed; a fresh clone or CI runner must be able to build without first running the host-Node generation step. **Implemented as a sibling script** (`generate-android-theme.mjs`, not an extension of `generate-scheme.mjs` itself) — verified reproducible and seed-propagating (task 2.5). One role (`shadow`) is filtered out of the emitted `ColorScheme` calls — current Compose Material3 no longer accepts it, confirmed via compile error, not assumed from the M3 role list `generate-scheme.mjs` already used for the web output.
- **Screen-to-component mapping** (visual layout/spacing/alignment/component placement mirrors the reference screen-exports 1:1 — see the Context section's PNG-vs-prototype authority split; content wording and interaction logic mirror the prototype, not the code level):
  - `Welcome`: large icon-in-tonal-container badge, generously spaced, headline + supporting line, a bottom-anchored trust-point list (three rows, leading icon + text), and a bottom-anchored full-width pill-shaped primary button — per `onboarding-1-welcome.png`. No back-arrow — entry point. Holds no state of its own (nothing to type, nothing to retain), so no ViewModel: "Get started" calls `navController.navigate()` directly, tested at the `androidTest`/UI layer, not as a separate unit test.
  - `ContactDetails`: top-left back arrow to Welcome (system back behaves the same) below an edge-to-edge status bar, headline + supporting line, two selection-card rows (Email selected/enabled with a tonal-purple fill and filled radio, SMS disabled "Coming soon" at reduced opacity), an `OutlinedTextField`-equivalent for email, a consent checkbox row, and a bottom-anchored full-width pill-shaped Continue button — per `onboarding-2-phone.png`.
  - `OtpVerify`: back arrow to Contact details, email retained on return (system back behaves the same) + 6 boxed digit fields, auto-advance focus on entry, auto-verify against the same mock code (`123456`) once all 6 are filled, wrong-code path allows up to 3 attempts with a "clear and retry" action before locking (the back arrow is the only recovery once locked — no separate in-body action), resend countdown (disabled while counting down, does not reset the attempt counter on use) — visual layout per `onboarding-3-otp.png`.
  - `SignedIn`: icon badge (check-circle) + mocked email display + Logout (clears state, navigates back to Welcome) + a caption noting this is a throwaway scaffold — content/wording per the prototype's `SignedIn.tsx`, visual layout per `onboarding-4-signedin.png`. No back-arrow in-screen — but Android always has a system back gesture/button regardless of in-screen UI, so this needs an explicit nav-graph decision, not just "no button drawn" (see Navigation below).
  - Implementation must diff each finished composable's screenshot against its corresponding reference PNG before being considered done (per the design-phase-plan's standing "diff against external references" rule) — see the new verification task in Section 10.
- **Navigation**: a single `NavHost` in `MainActivity`/`ChetnaApp` composable root, routes as sealed classes or `@Serializable` route objects (whichever `androidx.navigation-compose`'s current stable API expects at implementation time — verify via `verify-dependency-version` rather than assuming), one route per screen, matching the prototype's four routes (`welcome`, `contact`, `otp`, `signed-in`). **Back-stack semantics, not just screen-level back arrows** — the web prototype has no equivalent of a system back gesture, so this was invisible there and needs its own decision here:
  - Forward navigation `welcome → contact → otp` pushes normally (back arrow/system-back pops one level, per the screen mapping above).
  - `otp → signed-in` on successful verification navigates with `popUpTo(welcome route) { inclusive = false }` (clears `contact` and `otp` off the back stack, keeps `welcome` as the new bottom). This makes system back from Signed-in land on Welcome, not back into a completed/locked OTP screen — matching ordinary login-flow UX (you can't navigate backward into a finished auth step) and making Signed-in's "no back-arrow" choice consistent with what back actually does.
  - System back on Welcome (the graph's start destination, nothing below it on the stack) exits the app — default `NavHost` behavior, not intercepted; stated here so it's a verified, intentional outcome rather than an assumption.
- **Dockerized emulator, headless**: `apps/mobile/android/emulator/Dockerfile`, `FROM saschpe/android-emulator:35-jdk23.0.2_7`, with an entrypoint script that fixes `/dev/kvm` permissions, creates the `pixel_9` / API 35 AVD **on first container start if not already present** (not baked into the image — smaller image, one slower first boot instead of a slower rebuild every time), then launches the emulator with `-no-window`. The AVD directory persists via a named Docker volume so the first-boot cost isn't paid on every restart. **No display/VNC layer** — this container is for my own automated verification only (`adb screencap`, `connectedAndroidTest` via `docker exec`), not for a human to view. Tried adding one twice (noVNC, then scrcpy over an exposed adb port); both hit real rendering/latency problems specific to this environment that weren't worth continuing to fight once a human has a faster alternative (their own separate emulator, e.g. Android Studio, or physical-device sideload).
- **Test plan** (per `CLAUDE.md`'s testing philosophy, applied to this module — TDD, test before code, not just unit):
  - **Frameworks**: `test` source set uses JUnit5 + Kotest (matching the domain modules' existing convention, kept consistent across the codebase rather than defaulting to Android's more common JUnit4 for this layer — verify AGP's current JUnit5 support, or the `de.mannodermaus.android-junit5` plugin if needed, via `verify-dependency-version`). `androidTest` (instrumented) uses JUnit4 + `AndroidJUnit4`/`createAndroidComposeRule` — this is not a free choice, it's what Compose's UI-testing APIs are actually built on.
  - `test` source set: ViewModel/state-holder logic for screens that hold state — email validation and Continue-gating (`ContactDetails`), OTP digit-entry/attempt-counting/lockout/resend state machine (`OtpVerify`), logout/state-clearing (`SignedIn`). `Welcome` has no ViewModel (see screen mapping above) so has no corresponding unit-test task. Fast, no Android framework dependency beyond what's trivially fakeable.
  - `androidTest` source set: Compose UI tests (`createAndroidComposeRule`) for the interaction-heavy screens — OTP auto-advance/auto-verify/retry/lockout end-to-end within the UI layer, the Continue-button gating on email+consent, navigation actually occurring between screens (including `Welcome`'s tap-to-navigate, which lives only at this layer), a config-change (rotation) test confirming Hilt-provided ViewModel state survives via `ActivityScenario.recreate()`, and a back-stack test confirming system-back from Signed-in lands on Welcome rather than a popped `contact`/`otp` screen.
  - Both levels are represented as explicit, separate tasks in `tasks.md`, each preceded by its own "write the failing test" task — not bundled into a single "implement X" task with tests as an afterthought.
  - **Visual verification is separate from and in addition to functional testing**: `androidTest`/unit coverage proves the screens *behave* correctly, not that they *look* right. Each screen's finished composable must be screenshot-verified against its corresponding reference PNG (`design/prototype/reference/onboarding/welcome-and-auth/screen-exports/`) before being considered done — explicit tasks in Section 10, not assumed to follow automatically from green tests.
- **CI**: a new `.github/workflows/android.yml` (mirroring `docs.yml`'s shape) triggered on push/PR touching `apps/domains/**` or `apps/mobile/android/**`, running directly on the `ubuntu-latest` GitHub-hosted runner (which ships a preinstalled Android SDK — not inside a bare `gradle:*-jdk21` container, which has no SDK and would fail `assembleDebug` on the first run) via `./gradlew :mobile:android:testDebugUnitTest :mobile:android:assembleDebug` plus `:backend:build` to confirm the domain modules' new `android()`/`com.android.library` target hasn't broken backend's consumption of them — no instrumented/`androidTest` run in CI for this change (that needs an emulator/device runner, real cost/complexity beyond this change's scope; `androidTest` still gets written and run locally against the Dockerized emulator).

## Risks / Trade-offs

- [Risk] The local-only `chetna-emulator-a15-vnc` Docker image (13.5GB, produced this session via `docker commit` — a Docker snapshot command, not a git commit, and nothing checked into the repo) used to validate feasibility isn't reproducible outside this machine. → Mitigation: this design's "Dockerized emulator, made reproducible" decision above turns it into a real `Dockerfile`; the manual image was investigation, not the deliverable.
- [Risk] `androidx.navigation-compose`'s type-safe routing API has changed across recent versions (sealed classes vs. `@Serializable` objects) — this design doesn't pin the exact pattern. → Mitigation: apply `verify-dependency-version` at implementation time rather than guessing from training data, consistent with this repo's established discipline.
- [Risk] Creating the AVD on first container start (chosen, not baked into the image — see Decisions) means the first boot after a fresh `docker compose up` is slow (system-image + AVD setup, ~13GB worth of state, seen this session) — none of it is added to git/GitHub; it's local Docker state (image layers plus the named AVD volume) built/created on whichever machine runs the emulator. → Mitigation: the AVD directory is persisted in a named volume, so this slow step happens once per machine, not on every container restart; acceptable for a development-time tool outside any shipped artifact or CI path.
- [Risk] `androidTest` (instrumented) tests are real but not run in CI — a gap between "written" and "continuously verified." → Mitigation: explicitly named as a Non-Goal for CI in this change, not silently dropped; a future change can wire the Dockerized emulator (or a managed device) into CI once the cost is justified by more screens existing.
- [Risk] The Gradle wrapper's default `networkTimeout` (10s, `apps/gradle/wrapper/gradle-wrapper.properties`) is tight for a fresh distribution download running inside the Docker network path used by `apps/gradlew-docker` — observed failing once during this session's verification (container's raw `curl` throughput to the redistributed URL was fine, ~6MB/s, just slower than a 10s connect budget for a ~140MB file some of the time). → Mitigation: bump `networkTimeout`/add `retries` in `gradle-wrapper.properties` as part of task 1.2, or rely on the Gradle distribution being cached in the Docker volume after the first successful run either way — not a correctness issue, just worth not being surprised by on a slow connection.

## Open Questions

Resolved: the AVD-baking-vs-create-on-start question above was decided during review — create on first container start, persisted via a named volume (see the emulator Decisions bullet and its Risk).

Resolved during implementation (task 1.1's `verify-dependency-version` pass) — real version pins, cross-checked against Maven Central / Google's Maven / official compatibility docs, not assumed from training data:
- **AGP: 9.1.1**, not the newest stable 9.3.1 — Kotlin 2.4.10 (already fixed repo-wide for `domains`/`backend`, not something to bump just for this module) is only validated up to AGP 9.1.0/9.1.1 per the Kotlin Gradle plugin's own compatibility table. AGP 9.1.x's own minimum Gradle requirement (9.3.1) is satisfied by this repo's already-pinned Gradle 9.6.1.
- **Compose Compiler Gradle plugin (`org.jetbrains.kotlin.plugin.compose`): 2.4.10**, exactly matching the Kotlin version — this plugin ships in lockstep with Kotlin itself, no independent version to choose.
- **Compose BOM: 2026.06.01**, **`androidx.navigation:navigation-compose`: 2.9.8** (latest stable; 2.10.0 is still beta-only), **`androidx.hilt:hilt-navigation-compose`: 1.4.0**, **`com.google.dagger:hilt-android`/`hilt-android-gradle-plugin`: 2.60.1** — all current stable, no known coupling to the AGP/Kotlin ceiling above.
- **Hilt uses kapt, not KSP**, for annotation processing — a compatibility-driven choice, not a preference: KSP is a separately-versioned tool (unlike kapt, which ships bundled with the Kotlin Gradle plugin and is therefore automatically version-matched), and detekt's confirmed breakage on Kotlin versions as recent as 2.3.0 is a concrete example of exactly this class of tool lagging a fast-moving Kotlin release. kapt removes that risk entirely for a 4-screen module where kapt's slower annotation-processing isn't a real cost.
- **detekt: `2.0.0-alpha.6`**, not the stable `1.23.8` line — **no stable detekt release supports Kotlin 2.4.10** (1.23.8 targets Kotlin 2.0.21 and is confirmed broken on Kotlin 2.3.0's metadata format already); `2.0.0-alpha.6` is the only detekt build that targets 2.4.10. Approved explicitly by the user as a known trade-off against ADR-0015's original "standard, well-documented tooling" framing for detekt — worth re-checking once detekt 2.0.0 goes stable (see ADR-0015's "Revisit when").
- **JUnit5-on-Android**: `de.mannodermaus`'s `android-junit5` plugin, latest stable **2.0.1**, requires only AGP ≥ 8.2.0/Gradle ≥ 8.2 (both satisfied) — no Kotlin-version coupling found, unlike detekt.
