# ADR-0015: Android app module architecture — Navigation-Compose, Hilt, generated theme

- **Status**: Accepted
- **Date**: 2026-08-06

## Context

`apps/mobile/android` doesn't exist yet. The four Kotlin Multiplatform domain modules (`apps/domains/{consent,enforcement,credits,device}`) already carry the comment `// android() and ios targets are added when mobile scaffolding follows (ADR-0003)` in their `build.gradle.kts` — this module is anticipated, not novel.

[ADR-0003](0003-mobile-architecture.md) already locked native Kotlin + Jetpack Compose per platform (Compose on Android, SwiftUI on iOS later) — explicitly *not* a cross-platform Compose Multiplatform UI layer, only the domain/application layer is KMP-shared. That earlier decision resolves most of the navigation/DI ambiguity that would otherwise exist for a fresh Android app in 2026: the "Compose Multiplatform" ecosystem (Koin-in-composable-tree, Navigation 3) targets shared-UI-across-platforms, which isn't this app.

Chunk 1 (Welcome + Auth) is already validated as a React/MUI prototype (`design/prototype/src/screens/onboarding/`) — this ADR covers the native app's own architecture to build the real version of those same four screens, per [ADR-0013](0013-design-prototype-tooling.md)'s stated intention that the prototype's job is design communication, not a code source.

## Options considered

- **Navigation** — `androidx.navigation:navigation-compose` (chosen: the standard, Google-maintained Jetpack navigation for Compose, integrates directly with `hiltViewModel()`) vs. Compose Multiplatform's "Navigation 3" (rejected — built for KMP-shared UI across platforms, doesn't apply given ADR-0003's native-per-platform UI decision) vs. hand-rolled sealed-class routing (rejected — reinvents a solved, standard problem for no benefit).
- **Dependency injection** — Hilt (chosen: Google's standard DI for Android+Compose, `hiltViewModel()` scopes ViewModels to navigation destinations) vs. Koin (rejected — Koin's main advantage over Hilt is KMP-friendliness for *shared UI* code across platforms; doesn't apply here since only the domain layer is KMP-shared, not the UI) vs. manual constructor injection (rejected — unnecessary boilerplate once the app has more than a couple of screens and dependencies).
- **Module structure** — a single Gradle module `apps/mobile/android` with package-based feature separation (chosen — only 4 screens exist today; splitting into per-feature Gradle modules is a build-time/team-scaling optimization that doesn't apply yet) vs. multiple Gradle modules from day one (rejected as premature).
- **Compose theme sourcing** — generated from `design/tokens/` (chosen) vs. hand-written. ADR-0013 already decided this: the MUI prototype's `theme.ts` is a deliberately lossy, hand-written adapter, but the *real* Compose theme is supposed to be faithful. Concretely: extend `design/tokens/generate-scheme.mjs` (or add a sibling script in the same `design/tokens/` directory) to also emit a Kotlin `Color.kt` (M3 `lightColorScheme()`/`darkColorScheme()`, sourced from the already-generated `design/tokens/generated/color-scheme.json`) and `Shape.kt` (from `tokens.json`'s `shape.radius` values) directly into `apps/mobile/android/.../ui/theme/` — the same Node-based generation approach [ADR-0014](0014-design-token-generation-runtime.md) already justified, not a second tool. Typography is left at Compose Material 3's own defaults, matching `tokens.json`'s existing "M3 default type scale unmodified" note — nothing to generate there.
- **Code-quality guardrails** — detekt (chosen: the standard static-analysis tool for Kotlin) added at the `apps/` Gradle root, available to every module the same way `libs.versions.toml` already is, but enforced/blocking only for the new Android module's code. Retroactively cleaning up lint violations in `backend`/`domains` (neither of which has any lint tooling configured today) is explicitly out of scope for this change.
- **Android SDK + JDK provisioning** — containerized Gradle build (chosen) vs. host-installed SDK/JDK. **Corrected during implementation** (this ADR originally chose host-installed, on the reasoning that Android tooling is inherently host-native; that assumption didn't survive contact with this actual machine, which has no JDK anywhere and never has). The discriminating fact: this repo has *never* had a host JVM toolchain — `apps/backend/Dockerfile` already builds the backend's own Kotlin/JVM code inside a `gradle:8.11-jdk21` container, the most conventional "should obviously be on host" case there is, and it isn't. The earlier reasoning ("every mainstream Android workflow assumes a host SDK") was really about Android Studio-shaped workflows; this project doesn't use Android Studio, it invokes Gradle from a shell — exactly what the backend's Dockerfile already does. So the Android module follows the same precedent: all `./gradlew` invocations (build, test, detekt, `assembleDebug`) run inside a Docker container with JDK + Android SDK preinstalled — verified directly to work by mounting this repo into `saschpe/android-emulator:35-jdk23.0.2_7` (JDK 23, `sdkmanager`, platform-tools already present at `/opt/android-sdk-linux`) and running `./gradlew --version` against it successfully. This is **not** a third exception to ADR-0002's container-first default — it's that default being honored, correcting the earlier draft that would have been the exception. Host installs only `adb` (platform-tools, ~10MB) for the physical-device sideload step, which genuinely can't be containerized (needs USB access) — a call left to the user, since it's still a host install even if a small one. CI is unaffected by this correction: GitHub-hosted `ubuntu-latest` runners ship a preinstalled Android SDK already, so CI still runs directly on `ubuntu-latest`, not inside a bare `gradle:*-jdk21` container (which has no SDK and would fail `assembleDebug` immediately) and not inside the emulator image either (CI doesn't need the emulator's display/VNC layer, just SDK + JDK, and `ubuntu-latest` already has both).
- **On-device/emulator verification** — a Dockerized Android emulator (chosen) for development-time debugging, using this environment's confirmed `/dev/kvm` device and CPU virtualization support (16 cores with `vmx`/`svm` flags, verified directly) — the same role Playwright-in-Docker already plays for the web prototype (see ADR-0013): without a way to actually see rendered output, a report of "the screen is blank" from a physical device is nearly undebuggable. Physical-device sideload remains the final human sign-off, not a replacement for this.
  Concretely, three options were tried directly, not just researched:
  - `budtmo/docker-android:emulator_11.0` — worked immediately (proven `/dev/kvm` passthrough, bundled noVNC), but its free tier tops out at Android 11–14 (Android 15/16 support is paywalled behind the maintainer's sponsor-only "pro" image) and its bundled device skins are years-old (Nexus 4/5/One/S, Galaxy S6–S10) — rejected once actually inspected, not just because it was the first thing tried.
  - `ReactiveCircus/docker-android-images` — checked as a more reputable alternative; rejected, tops out at API 30 (Android 11), no VNC/display support at all (headless CI-only by design).
  - `saschpe/android-emulator:35-jdk23.0.2_7` (chosen) — genuinely current (Android 15 / API 35), ships the raw SDK with no pre-baked AVD or display layer, so both had to be built on top: an AVD created via `avdmanager` against the `pixel_9` device profile and the `system-images;android-35;google_apis;x86_64` package, and a VNC-viewable display added by running the emulator against `Xvfb` (not `-no-window`) with `x11vnc` + `websockify`/noVNC layered on top (none of these were pre-installed in the image). Also needed `chmod 666 /dev/kvm` inside the container — the image runs as a non-root `nonroot` user not in the container's `kvm` group, unlike `budtmo`'s image which ran as root throughout.
  - The resulting setup (system image + AVD + installed VNC packages) was committed to a local image (`chetna-emulator-a15-vnc`) so this doesn't have to be rebuilt from scratch — see `apps/mobile/android`'s README (once scaffolded) for the run command.

## Decision

- Navigation: `androidx.navigation:navigation-compose`.
- DI: Hilt.
- Module structure: single Gradle module `apps/mobile/android`, package-based feature separation (e.g. `in.chetna.mobile.onboarding.welcome`, `.contact`, `.otp`, `.signedin`).
- Compose theme: `Color.kt`/`Shape.kt` generated from `design/tokens/` via an extension to the existing Node token pipeline; Typography left at Compose M3 defaults.
- Code quality: detekt added at the `apps/` Gradle root, enforced on the new Android module's code only.
- SDK + JDK provisioning: containerized — all `./gradlew` invocations for `apps/mobile/android` run inside `saschpe/android-emulator:<verified tag>` (or an equivalent JDK+Android-SDK image) with the repo mounted, via a documented wrapper script (`apps/gradlew-docker`, see the OpenSpec change's tasks), not a host install — this honors ADR-0002's container-first default rather than exempting from it. Host installs only `adb` (platform-tools) — approved as a narrow host install for the physical-device sideload step, which needs USB access a container can't provide. CI uses GitHub-hosted `ubuntu-latest` runners' preinstalled SDK directly, unaffected by this decision.
- Verification tooling: a **headless** Dockerized Android emulator (`saschpe/android-emulator:35-jdk23.0.2_7` base, Android 15, `pixel_9` device profile) for my own automated checks only (`adb screencap`, `connectedAndroidTest`) — no display/VNC layer. **Reversed from an earlier VNC-viewable design**: a human wanting to see the app live doesn't view into this container at all; they run their own separate emulator (e.g. Android Studio, hardware-accelerated) and install the APK there directly, or use physical-device sideload for final sign-off. Tried making the container itself human-viewable first (noVNC, then scrcpy over an exposed adb port) — both hit real, unresolved rendering/latency problems specific to routing a software-rendered emulator's display through Docker+X11+remote-viewing; not worth the complexity once a human has a faster, simpler alternative already available.
- SDK levels: `compileSdk = 37`, `minSdk = 26` (Android 8.0, released 2017), `targetSdk = 37`. `minSdk` was an implementation-time call (nothing upstream of this ADR specified it), user-approved as a starting floor, together with a standing policy for what happens when it conflicts with a specific feature later: **evaluate per feature, not by raising the floor by default.** If a future feature needs an API level above 26 and is core to the product, raise `minSdk` then (a deliberate, evaluated change, not a default reflex). If it's not core, gate the feature behind a runtime API-level check (`Build.VERSION.SDK_INT`) that disables it on older devices with a clear "requires Android X or newer" message, rather than excluding those users from the whole app. Don't pre-emptively raise `minSdk` for a feature that hasn't been built yet.

## Consequences

- Standard, well-documented Android/Compose stack — no bespoke tooling to maintain, consistent with how the backend already leans on mainstream Spring Boot conventions rather than inventing its own.
- The domain modules' `kotlin {}` blocks need an `android()` target added (already anticipated by their own comment) before `apps/mobile/android` can depend on them. This is not purely additive to the build graph: applying `com.android.library` to each domain module puts the Android Gradle Plugin — and therefore an Android SDK requirement — on the classpath of every module that depends on them, including `apps/backend`. `apps/backend`'s own build must be verified to still succeed unchanged after this; it is not a safe assumption.
- No new exception to ADR-0002's container-first dev-tooling default is created — an earlier draft of this ADR had proposed one (host-installed Android SDK) before implementation revealed this machine has no host JDK at all and never has, matching `apps/backend`'s existing Dockerized-Gradle-build precedent. `adb` alone (platform-tools, ~10MB) is host-installed, for the physical-device sideload step only. The root README needs a new section documenting the containerized build/run workflow (`apps/gradlew-docker` wrapper, emulator compose, adb) once it exists — tracked in the OpenSpec change's tasks, not done as part of this ADR.
- A second generated-theme step now exists alongside the MUI prototype's adapter and the web `color-scheme.json` generation — three consumers of the same `design/tokens/` source, which is exactly the durability ADR-0013 designed for, not new risk.
- detekt exists in the repo for the first time; `backend` and `domains` remain unlinted until a separate, deliberate cleanup pass adopts it there too.
- Dockerized Android emulators are a genuinely less common setup in a WSL2 + Docker environment than the Playwright pattern was; first-time setup needed real validation, not just an assumption it works — validated directly (see Options above).
- The working emulator setup currently exists only as a manually-`docker commit`-ed local image on this machine, not a reproducible `Dockerfile` in the repo — real follow-up debt, not a finished deliverable. Turning the exact steps above (system image install, `avdmanager create avd`, Xvfb/x11vnc/noVNC) into a proper `apps/mobile/android/emulator/Dockerfile` (or similar) is part of the `scaffold-android-onboarding-chunk1` OpenSpec change's tasks, not deferred indefinitely.

## Revisit when

Build times or team size make the single-module structure untenable (split into per-feature Gradle modules then). `backend`/`domains` get their own dedicated lint cleanup pass (expand detekt enforcement to them at that point, not before). The headless Dockerized emulator proves too unreliable for my own automated checks (not the human-viewability question, already settled above) — fall back to physical-device-only iteration for those checks too. detekt ships a stable release supporting Kotlin 2.4.10+ (confirmed during implementation that no stable detekt release does today, only `2.0.0-alpha.6` — re-pin to stable once one exists, since the alpha was a user-approved trade-off, not a permanent choice). A specific core feature turns out to need an API level above 26 (raise `minSdk` then, evaluated per feature per the SDK levels decision above — not preemptively).
