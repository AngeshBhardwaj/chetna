# ADR-0010: Authentication & authorization — phone+OTP login, device pairing, JWT via Spring Security

- **Status**: Accepted
- **Date**: 2026-07-21

## Context

"Auth" bundles several distinct problems for this product: how a parent/guardian logs in, how a child's device gets authenticated (not the same thing as a login), how tokens get issued, and how authorization is scoped given multi-child/multi-parent households ([v1 feature set](../../brainstorm/v1-feature-set.md)) and the DPDP consent model ([competitive landscape research](../../planning/research/competitive-landscape.md)).

## Options considered

- **Parent login — phone + OTP vs. email + password vs. both**: phone + OTP is the dominant Indian consumer-app pattern (more trusted than passwords, no password-fatigue/reset flows to build). Supporting both from day one adds a second full credential flow (including password reset) for marginal benefit at this stage.
- **Token issuance — simple JWT via Spring Security vs. a full self-hosted OAuth2/OIDC Authorization Server** (e.g. Spring Authorization Server): a full Authorization Server is the standards-compliant choice if third-party developers will ever consume the API on a user's behalf, but no such need exists yet — only first-party clients (our own mobile/web apps). Running a separate identity-provider product now would be the same kind of premature infrastructure the modular-monolith philosophy ([ADR-0004](0004-modular-monolith.md)) already argues against.
- **Child device authentication — a full "child login" vs. a device-pairing flow**: children (especially the toddler persona) don't have independent credentials to log in with. A pairing flow (parent app generates a short-lived, single-use code/QR; the child's device consumes it once during setup and receives its own long-lived device credential) avoids ever handing the child's device the parent's actual login credentials, and matches the pattern used by Family Link and every commercial competitor.

## Decision

- **Parent/guardian login**: phone number + OTP as the primary and only first-party credential. "Sign in with Google/Apple" is available as an optional convenience layer via Spring Security's OAuth2 *client* support (consuming an external identity provider — a much smaller thing than running our own).
- **Device pairing**: a short-lived, single-use pairing code/QR generated by the parent's app; the child's device exchanges it once for its own long-lived device credential. The device is a registered entity under the family account, never "logged in as the parent."
- **Token issuance**: JWT access + refresh tokens issued directly by our Spring Security backend — no separate Authorization Server product.
- **Authorization model**: role-based (Guardian, Co-Guardian for multi-parent households, and a deliberately narrow Child role for the own-device persona's "ask for more time" flow), scoped to the Family/Household aggregate — a guardian can only see/act on their own family's data. Sensitive operations (e.g. enabling the phase-2 face-ID feature) are additionally gated on consent-state, not role alone, tying directly to the Consent/Guardianship bounded context already established as first-class in the DPDP research.

## Consequences

- No password-reset/credential-recovery flow to build for v1 — OTP delivery (SMS reliability, rate-limiting/anti-abuse) becomes the operational concern to get right instead.
- No separate identity-provider service to run or maintain; less infrastructure, consistent with the modular-monolith philosophy.
- Device-pairing flow needs its own careful design (code expiry, single-use enforcement, revocation if a device is lost/replaced) as part of architecture scaffolding.
- **DigiLocker integration is a business/process dependency, not just an engineering task**: DPDP Rule 10's approved verification methods include DigiLocker, but integrating with it requires formal registration/approval as a Requester entity in DigiLocker's partner ecosystem — a lead time separate from and likely longer than the engineering work itself. Given the DPDP Act's 18-month compliance clock, this registration process should start early rather than being treated as something to wire up when the consent flow is being built.

## Revisit when

A genuine need for a full OAuth2/OIDC Authorization Server appears — e.g. third-party developers needing to consume the API on a user's behalf — not preemptively. Revisit phone+OTP-only if SMS deliverability/cost in practice proves unreliable enough that an email fallback becomes necessary.
